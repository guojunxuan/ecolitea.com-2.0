# Resource storage prefix migration

Payload owns resource records and lifecycle hooks. The S3 storage adapter owns object keys; public delivery uses the configured R2 public URL. Media, Site Assets and Documents use `media/`, `site-assets/` and `documents/`. Documents starts with its prefix and is **never an input to this migration**.

The installed `@payloadcms/plugin-cloud-storage/utilities` public `getFileKey` export supplies the exact key normalization used by the installed S3 upload/delete implementation. Document prefix overrides collection prefix; an empty/missing prefix falls back to the collection prefix. `generateR2FileURL` encodes each key segment once, including Chinese characters and spaces. The plugin always inserts storage fields, including when R2 is disabled for isolated tests, so generated types remain stable.

## Operational contract

`scripts/migrate-resource-prefixes.ts` is an explicit maintenance tool, not an application startup migration. It has separate `inventory`, `copy`, `update`, `verify`, `remove-originals`, and `purge-media-versions` stages. Default operation is dry-run: resource/storage writes require `--execute`; only the local manifest is written during inventory. No deletion stage runs automatically. The tool disables automatic collection/index creation and production migrations in its own Payload initialization.

The environment report requires an explicit, valid database name in the MongoDB URI and prints the database host and canonical database name without credentials, bucket, endpoint and public base URL **before a connection**. Encoded database names are decoded once and normalized for approval. After connecting, the tool checks the driver-selected database name against that approved name before existing connection hooks or any operational read/write; an implicit default or mismatch is refused. `--environment` returns after reporting and performs no connection. Each subsequent command requires the reported `--expected-target` fingerprint. Write commands also require the exact inventory digest and `--maintenance-window`, attesting that all other writers are stopped. The fingerprint is an environment binding, not authorization: the operator must obtain the required environment-specific approval first. Never run against an environment merely because a command is present here.

No project dependency was added. The operational S3 port resolves the SDK owned by the installed `@payloadcms/storage-s3` package, and supports HEAD, conditional COPY and DELETE. This deliberately isolated ownership boundary must be rechecked when upgrading the adapter. Application file endpoints continue to use native Payload storage delivery. The tests run the actual installed upload hook against an in-memory HTTP request handler; they do not open sockets or connect to MongoDB/R2.

## Maintenance window and deployment order

1. Back up the database, storage and the old application release. Stop all application instances, Admin writes, jobs, APIs, seeds and upload clients. Keep the public site in maintenance mode. Do not expose the new prefix rules to writes before copying and updating are complete.
2. From the migration checkout, run the environment-only report. Present that exact database/bucket/endpoint/public URL to the controller and obtain approval for that environment. The CLI uses legacy root fallback for Media/Site Assets **only inside its maintenance process**, installed before Payload builds its storage hooks. The live old deployment remains stopped. Inventory reads exact persisted metadata through Payload's native database adapter before URL `afterRead` hooks; root URLs must match source keys. Never inventory a deployment after the new fallback has already obscured legacy root URLs.
3. Create a new inventory manifest. Full pagination covers Media and Site Assets, including trashed records and legacy size files. HEAD each original/size; include current and historical Media references from `findMediaReferences` and full Media-version backups. The historical five missing filenames and “99 versions” are hints only: review the freshly observed IDs, filenames, missing objects, references and counts. No historical name or count authorizes deletion.
4. Review the report, back it up outside the checkout, and approve its exact digest. Reconcile shared root keys, missing originals, destination collisions and source URL/key mismatches. The complete source/destination key plan must have unique ownership: any cross-file source/destination overlap is rejected, even when bytes match. A file may retain its own unchanged key. This check runs before inventory is saved and again before every stage, so historical manifests cannot authorize copying over a needed source or deleting another resource's destination. Missing records are skipped by copy/update/verify and are preserved. Missing Site Assets require manual repair. Missing Media with a live original/size/destination, current reference, or incomplete inspection cannot be removed by this tool. Keep the same manifest for resumes; do not edit its immutable inventory.
5. Execute `copy`, then `update`, each separately. COPY preserves the source. Existing destinations must match source ETag/size; collisions stop the stage. All files of a record must be copied before updating that record's prefix, original URL and size URLs through Payload. A failed copy never authorizes update; a failed update leaves source and copy intact. Update rereads stored metadata before marking completion. If historical size metadata is no longer writable under the current Payload schema, it stops for an explicitly reviewed schema repair instead of silently dropping metadata. Stop on any failure and retain maintenance mode. Missing records require an explicit reconciliation/deletion decision before reopening service, because the new upload/delete fallback would otherwise target a different key.
6. Deploy the new application release while writers are still stopped. Execute `verify`: every migrated record must have the planned persisted metadata, identical destination size/ETag, and a new public address returning HTTP **200** without a redirect. GET bodies are cancelled rather than downloaded. Compare the deployed application URLs with the manifest as part of the release check. Keep originals throughout this step.
7. Review source URL references. `remove-originals` rechecks HTTP 200, stored metadata, object metadata, all persisted current/version content, raw Media version backups, and source files under `src`, `public`, `docs`, `scripts` and README. Hardcoded full source URLs block deletion. Resolve content/asset hardcodes under a separately reviewed change or retain originals; also audit external consumers outside this repository, which the script cannot discover. This scan is conservative; shared Media IDs use the existing scanner and exclude only its exact operational lock collection.
8. Obtain **separate approval** to remove source objects, then invoke only `remove-originals` with its distinct confirmation. Missing Media record deletion is never inferred from an absent object: explicitly list newly reviewed IDs with `--delete-missing-media`. The tool rescans current references immediately before this phase, reports historical references, checks that all its original/size source and destination keys are absent, and uses Payload deletion so its normal protection hooks still apply. Trashed/live content is not rewritten to permit deletion.
9. Obtain **another explicit approval** for Media version deletion and report the current target database and freshly counted IDs. `purge-media-versions` is an independent operational repair, not a content deletion API: versions are disabled, so Payload has no live version model. It accesses only Mongo's `_media_versions` collection, checks adapter naming, binds live IDs and full contents to the approved manifest, and deletes only those IDs. It never deletes Page/Post/Blog/Global versions. New or changed Media versions cause refusal; partial prior deletion is resumable. Full BSON Extended JSON backups remain in the manifest. Old Media-version URLs may block step 8, in which case this separately approved step must occur first or source objects must remain.
10. Reopen writes only after migrated records and missing-record decisions are complete and verification passes. Original cleanup and version purge can be postponed; keep their approvals separate. Archive the final manifest, approvals, database backup and release identifiers securely. Never commit operational reports or credentials.

Example commands below use **reviewed placeholders**, not project environment values. Do not copy them as evidence of approval:

```bash
corepack pnpm exec tsx scripts/migrate-resource-prefixes.ts --environment
corepack pnpm exec tsx scripts/migrate-resource-prefixes.ts --stage=inventory --report=/secure/path/resource-prefixes.json --expected-target=REVIEWED_TARGET_FINGERPRINT
# Inspect the inventory; capture its digest and obtain approval before writes.
corepack pnpm exec tsx scripts/migrate-resource-prefixes.ts --stage=copy --report=/secure/path/resource-prefixes.json --expected-target=REVIEWED_TARGET_FINGERPRINT --expected-inventory=APPROVED_DIGEST --execute --maintenance-window
# Repeat explicitly for update, then deploy the new release while writes stay stopped.
# Repeat explicitly for verify, still with execute to persist verification checkpoints.
# After separate source-removal approval:
corepack pnpm exec tsx scripts/migrate-resource-prefixes.ts --stage=remove-originals --report=/secure/path/resource-prefixes.json --expected-target=REVIEWED_TARGET_FINGERPRINT --expected-inventory=APPROVED_DIGEST --execute --maintenance-window --confirm=remove-originals
# Only after separate Media-version purge approval:
corepack pnpm exec tsx scripts/migrate-resource-prefixes.ts --stage=purge-media-versions --report=/secure/path/resource-prefixes.json --expected-target=REVIEWED_TARGET_FINGERPRINT --expected-inventory=APPROVED_DIGEST --execute --maintenance-window --confirm=purge-media-versions
```

Dry-run stages do not mark a record copied/updated/verified and cannot authorize later removal. A report path already present cannot be overwritten by a new inventory. Store the report outside scanned source directories; it intentionally includes old URLs and sensitive content backups.

## Manifest, resumption, and rollback

The JSON manifest contains its schema version, exact target, creation time, inventory digest, immutable per-record collection/ID, original prefix/URL/size metadata (`before`), fields originally absent (`absentFields`), planned metadata (`after`), every source/destination key and URL, source HEAD size/ETag, current/historical reference report, full BSON Extended JSON Media version backups, progress flags and timestamped events. Local writes use a private-mode temporary file and atomic rename. Protect it like a database backup. Its digest detects accidental inventory edits and binds approval to the observed records; it is not a digital signature against a hostile operator.

COPY reruns accept an existing matching destination without copying again. UPDATE reruns accept exact planned stored metadata without updating again. A failure after a database update but before its local checkpoint is recovered by that same metadata comparison. VERIFY repeats live checks. Source removal reruns permit an already absent original, and version purge reruns accept a subset of approved, unchanged version records. A failed action leaves earlier checkpoints intact; the next command revalidates live state before proceeding. Resume with the same approved manifest, never by silently regenerating one after a partial write.

Before original deletion, rollback is: keep writers stopped; verify original keys still match the logged size/ETag; restore each changed resource's `before` fields through a reviewed Payload maintenance operation under legacy storage rules with no upload file; restore genuinely absent fields using the logged `absentFields` through a narrowly scoped operational repair if exact absence is required. Restore the old release, validate the original URLs, and reopen writes only after verification. Keep destination copies for investigation; rollback does not delete them automatically. No automatic rollback executes after an error.

After source removal, first restore the original objects from the backup or verified destination copies at their logged source keys and validate them, then perform the metadata/release rollback above. Version restoration is a separate approved Mongo repair using the manifest's BSON Extended JSON backups and exact original IDs; use EJSON deserialization to preserve ObjectIds/dates and refuse overwriting a live ID. Missing-record deletion requires the pre-window database backup for full restoration; `before` records only storage metadata, not complete resource documents. Do not approve missing-record deletion without that backup.

The copy verifier deliberately requires ETag equality and size equality. If an existing multipart object or provider behavior changes ETag on copy, it stops rather than assuming byte equivalence; retain originals and review a checksum-based migration separately. Mutation safety assumes the declared maintenance window holds: the tool does not acquire a distributed lock or manage external upload clients.
